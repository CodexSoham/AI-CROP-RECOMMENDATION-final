# 📜 Project Constitution: AdaptiveCrop AI

> **System Pilot Protocol:** B.L.A.S.T. (Blueprint, Link, Architect, Stylize, Trigger) & A.N.T. 3-Layer Architecture  
> **Repository:** `Adaptive Crop Recommendation`  
> **Status:** Initialized (Protocol 0)

---

## 1. Architectural Invariants

1. **Deterministic ML Over Probabilistic Hallucinations:**
   - Crop suitability predictions must be generated by calibrated deterministic ML models (e.g., Random Forest / XGBoost / Ensemble).
   - Large Language Models (Gemini API) are strictly used for **explaining** recommendations, contextualizing agronomic factors, and generating farmer-friendly advisory notes—**never** for generating raw crop suitability scores.

2. **A.N.T. 3-Layer Architecture:**
   - **Layer 1: Architecture (`architecture/`):** Technical SOPs in Markdown defining data contracts, error bounds, and tool logic.
   - **Layer 2: Navigation (Decision Engine):** Orchestrates workflows, calling tools sequentially and routing payloads.
   - **Layer 3: Tools (`tools/`):** Atomic, deterministic scripts (Python / Node / TypeScript) tested with isolated inputs and outputs.

3. **Separation of Intermediates & Payloads:**
   - Ephemeral/scraped data and intermediate artifacts live strictly in `.tmp/`.
   - Production payloads reside in verified datastores (Supabase PostgreSQL, Client UI State).

4. **Real-World Constraint Layer:**
   - Raw ML probabilities are adjusted through a deterministic **Constraint Engine** (accounting for water availability, seasonal rainfall forecast, budget, and soil restrictions) before final top-3 ranking.

---

## 2. Behavioral Rules & Operating Principles

1. **Confidence Score Calibration:**
   - Never label raw softmax probabilities as absolute real-world confidence without calibration and constraint adjustments.
   - Distinguish between **ML Agronomic Suitability** and **Constrained Practical Feasibility**.

2. **Self-Annealing Loop:**
   - On tool or execution error: Analyze the stack trace -> Patch the tool in `tools/` -> Verify with test execution -> Document learned constraints into `architecture/`.

3. **Data-First Invariant:**
   - No feature or tool may be built without an explicit schema defined here in `gemini.md`.

## 3. Data Schemas (Input / Output Shapes)

### 3.1 Raw Field Input Schema (`FieldInputPayload`)
```json
{
  "location": {
    "latitude": 16.8524,
    "longitude": 74.5815,
    "regionName": "Sangli, Maharashtra"
  },
  "soil": {
    "nitrogen": 82.0,      // N in mg/kg or kg/ha
    "phosphorus": 48.0,    // P in mg/kg or kg/ha
    "potassium": 41.0,     // K in mg/kg or kg/ha
    "ph": 6.7              // 0 - 14 scale
  },
  "environmental": {
    "temperature": 28.4,   // °C (from Open-Meteo or user sensor)
    "humidity": 73.0,      // % relative humidity
    "rainfall": 812.0      // mm annual / seasonal cumulative
  },
  "constraints": {
    "waterAvailability": "medium", // "low" | "medium" | "high" | "irrigated"
    "farmerBudget": "moderate",    // "low" | "moderate" | "high"
    "riskTolerance": "balanced",   // "conservative" | "balanced" | "aggressive"
    "season": "kharif"             // "kharif" | "rabi" | "zaid"
  }
}
```
